Enterprise Knowledge Cycle Platform｜Requirements Definition

社内ナレッジ循環基盤 要件定義書

人 × AIで知見を標準化する循環型ナレッジ基盤。承認済み企画を、業務・機能・AI・データ・権限・監査・PoC要件へ具体化した要件定義書。

1. 目的・背景

日々の業務で生まれる経験・判断・失敗・工夫・技術的気づきを、単なる文書保管ではなく、収集 → 統合 → 構造化 → 知見候補化 → 人レビュー → 承認 → 再利用 → 効果検証まで循環させる。

解決する課題

  • ベテラン・特定担当者への問い合わせ集中
  • 過去資料探索に時間がかかる
  • 同じ失敗・同じ検討が繰り返される
  • 知見が現場・個人・文書に分散する
  • 教育・標準改訂へ知見が反映されにくい

実現する状態

  • 根拠付きで過去知見を検索・再利用できる
  • AIが整理役・比較役・レビュー補助役を担う
  • 人が技術判断・承認・標準化の責任を持つ
  • 利用実績と効果が次の改善材料として蓄積される

2. 対象範囲

区分対象備考
一次情報日報、設計検討、施工上の工夫、トラブル、改善案、会議、写真、図面、文書、設計計算書、検討書等企画書に例示された情報源を対象候補とする
情報源連携Slack、社内文書・共有ストレージ、Google Drive / Microsoft 365、CDE・BIM/CIM、施工管理、安全・品質記録等PoCでは対象を限定し段階連携
AI処理統合、抽出、分類、タグ付け、類似検索、候補生成、レビュー支援、標準改訂支援、効果分析自動確定は禁止
人の業務事実確認、技術レビュー、適用範囲判断、例外判断、正式承認、標準発行Human-in-the-loop必須
PoC情報収集 → AI構造化 → 知見候補 → 人レビュー → 検索利用標準改訂自動化は第2段階
対象外：AI単独による技術判断の確定、出典不明情報の正式知見化、承認なしの社内標準自動改訂。

3. 基本原則

Evidence First

AI回答・知見候補・レビュー結果は、元資料・根拠・版へ追跡可能とする。

Human Authority

正式知見、適用範囲、例外条件、標準化は、人の承認を必要とする。

Continuous Cycle

利用結果・採否・効果指標を蓄積し、次の知見候補生成・レビュー改善へ戻す。

4. 利用者・役割要件

ロール責務主な権限
一般利用者検索、参照、一次情報登録、フィードバック閲覧、登録、自分の登録内容修正
技術レビュー担当技術的妥当性、適用条件、例外条件、表現の確認レビュー、差戻し、コメント、承認依頼
専門分野責任者高度・重要案件の判断上位レビュー、承認・却下
標準管理者標準書・チェックリスト・教育資料への反映判断標準改訂案の承認・発行管理
システム管理者利用者、権限、連携、監査、保守管理機能全般。ただし技術承認権限とは分離可能
AI/データ管理者AI設定、検索品質、データ品質、モデル・プロンプト管理AI設定変更、再処理、品質評価

5. 業務要件

1 記録一次情報登録
2 統合関連情報収集
3 構造化項目抽出
4 候補化知見ドラフト
5 AIレビュー根拠・不足・矛盾
6 人レビュー承認・差戻し
7 標準反映改訂候補
8 効果検証利用・品質評価

業務ルール

  • 一次情報の事実性は登録者または情報責任者が担保する。
  • AIは不明条件を無断補完せず、「不明」「要確認」として扱う。
  • 承認済み知見は承認者、承認日時、根拠、適用条件、版を保持する。
  • 条件・根拠・基準版の変更時は、影響する承認済み知見を再確認対象にできること。
  • 採用・却下・差戻し理由を記録し、品質改善データとして再利用する。

7. AI要件

AIが実行してよいこと

  • 抽出・分類・タグ付け
  • 類似度判定・重複候補提示
  • 知見候補ドラフト生成
  • 根拠候補と類似事例提示
  • 矛盾・不足・旧版基準の警告
  • レビュー観点・チェック項目提示
  • 利用実績と効果指標集計

AIに任せないこと

  • 技術判断の最終確定
  • 適用範囲・例外条件の最終決定
  • 正式知見への自動昇格
  • 公式標準の自動発行
  • 根拠のない条件補完

AI品質要件

  • 回答・知見候補ごとに根拠情報を提示する。
  • 根拠が見つからない場合は、その旨を明示する。
  • AI信頼度は参考指標として保持し、承認の代替には使わない。
  • プロンプト・モデル・検索設定の変更履歴を追跡可能にする。
  • 誤情報、採否、差戻し理由を評価データとして保存できる。

8. データ要件

カテゴリ主要項目要件
識別ナレッジID、タイトル、版、ステータス一意識別・履歴追跡
出所元情報、出典、原文参照、発生案件・現場原文へ戻れること
分類工種、業務分類、設備、タグ複数分類・後編集可能
技術内容課題・事象、原因、対応、結果、成功/失敗構造化＋原文保持
適用性適用条件、注意条件、適用不可条件検索回答時に必ず考慮
根拠基準・仕様・版、根拠資料、関連事例参照切れ検出・版追跡
統制AI信頼度、レビュー者、承認者、承認日時監査証跡として保存
評価利用回数、評価、再利用先、効果、採否理由継続改善へ利用
原文データとAI生成データは混同せず、「原文」「AI抽出」「AI生成」「人修正」「承認済み」を識別できる属性を持つ。

9. 承認ワークフロー要件

  1. 情報登録
  2. AI構造化
  3. 知見候補生成
  4. AIレビュー支援
  5. 技術担当者レビュー
  6. 必要時、専門分野責任者へエスカレーション
  7. 承認済み知見へ昇格
  8. 標準化対象は別ワークフローへ送付
  9. 発行後の利用・効果追跡

状態

状態意味
Draft一次情報・編集中
AI-ProcessedAI構造化済み
Review-Pending人レビュー待ち
Returned差戻し
Approved承認済み正式知見
Rejected却下・非採用
Revalidation-Required基準版・条件変更等により再確認が必要
Archived旧版・廃止・参照専用

10. 検索・活用要件

  • キーワード、分類、案件、工種、期間、ステータス、承認状態で絞り込み可能。
  • 自然言語質問を受け付ける。
  • 検索回答は、承認済み情報を優先表示する。
  • 回答には、根拠資料、引用元、適用条件、例外条件、版、承認状態を併記する。
  • 未承認情報を使用する場合は「参考情報」であることを明示する。
  • 回答から元資料・関連知見・類似事例へ遷移できる。

11. セキュリティ・権限要件

  • 閲覧・登録・編集・レビュー・承認・管理の権限を役割別に制御する。
  • 機密情報・個人情報は権限、マスキング、保持期間を設定可能にする。
  • 情報源側のアクセス権を無視して横断公開しない。
  • AI処理対象外とする機密区分を設定できる。
  • 管理者操作、権限変更、承認操作を監査記録する。
  • 技術承認権限とシステム管理権限は、必要に応じて職務分離できる。

12. 監査・版管理要件

  • 誰が、いつ、何を、どの根拠で、どの状態からどの状態へ変更したか記録する。
  • 知見本文、適用条件、根拠、分類、承認状態の変更履歴を保持する。
  • 基準・仕様の版数を管理する。
  • 旧版知見を削除せず、原則として履歴参照可能にする。
  • AIモデル・AI設定・プロンプト・検索設定の変更履歴を保持する。

13. 非機能要件

ID分類要件
NFR-01可用性PoCは業務検証に必要な稼働を確保。本番SLAは展開段階で決定。
NFR-02性能通常検索・一覧・詳細画面は業務利用を阻害しない応答性を目標とし、AI処理は進捗表示を行う。
NFR-03拡張性情報源、分類、AIモデル、検索方式を交換・追加できる疎結合構成とする。
NFR-04保守性ルール、プロンプト、分類体系、承認経路をコード改修最小で変更できる。
NFR-05可観測性処理失敗、連携失敗、AI失敗、検索品質、レビュー滞留を監視可能にする。
NFR-06バックアップ承認済み知見、メタデータ、監査ログ、設定の復旧手段を持つ。
NFR-07アクセシビリティPCを基本に、主要操作は一般的なブラウザで利用可能とする。
NFR-08説明可能性AI出力について、参照根拠・検索元・処理状態を利用者が確認できる。

14. 連携要件

企画書で挙げられた情報源を「連携候補」とし、PoCでは対象テーマに必要なものだけを選定する。

入力連携

  • Slack
  • 社内文書・共有ストレージ
  • Google Drive / Microsoft 365
  • CDE・BIM/CIM
  • 施工管理、安全・品質記録
  • 写真、動画、図面、設計計算書

連携共通条件

  • 元情報ID・URL・版・更新日時等を保持
  • 差分取得・再取込を考慮
  • アクセス権を継承または同期
  • 連携エラーを記録・再処理可能
  • 連携対象外データを指定可能

15. PoC要件

PoCは1テーマ・1部門・限定データで実施し、知識循環が実際に回るかを確認する。

設計照査・設計検討ノウハウ
仮設計画・施工計画の過去事例
品質不具合と再発防止
現場改善・省力化事例
技術問い合わせと回答履歴
2年次教育等の技術教育Q&A

PoC必須機能

登録、AI構造化、知見候補生成、AIレビュー支援、人レビュー・承認、自然言語検索、根拠表示、基本監査ログ、KPI計測。

16. KPI・受入基準

領域指標PoC合格基準
登録登録件数・登録者数・情報欠落率要PoC開始前確定
検索回答到達時間・検索成功率・再検索率要確定
AI品質分類精度・根拠提示率・誤情報率要確定
レビューレビュー時間・差戻し率要確定
再利用参照回数・類似案件への再利用率要確定
業務効果資料作成・問い合わせ・手戻り削減要確定
品質同種不具合再発率・標準逸脱件数要確定
学習利用者評価・採用/却下理由蓄積率要確定
受入の共通必須条件：AI出力を人が承認せず正式知見化できないこと、根拠へ追跡できること、未承認情報と承認済み情報がUIで識別できること。

17. 導入ロードマップ

Phase 1｜PoC

限定テーマで収集・構造化・検索・レビューを検証。

Phase 2｜技術部門展開

複数分野へ拡張し、承認済み知見DB・レビュー運用を整備。

Phase 3｜標準・仕様連携

社内標準、チェックリスト、教育資料の改訂候補をAI生成。

Phase 4｜全社循環

設計・施工・品質・安全・DX・教育を横断し継続更新。
